# 升级、备份与恢复

更新使用新版本中的 `deploy/portable/manage.py`，在服务器上运行。程序镜像替换后，原数据、账号、AI 配置、加密主密钥和日历订阅凭据继续使用原挂载目录。已有安装不要重新执行 `init`。

先将新源码放入单独的版本目录，构建候选镜像，并使用合成数据验证。确认后生成更新计划；以下路径和镜像名需替换为实际值：

```sh
docker build -t jindu:0.15.0 /srv/jindu/releases/0.15.0
python3 /srv/jindu/releases/0.15.0/deploy/portable/manage.py plan \
  --compose /srv/jindu/compose.yaml --image jindu:0.15.0 \
  --state-dir /srv/jindu/updates --output /srv/jindu/updates/plan-0.15.0.json
```

检查计划中的旧容器、目标镜像、数据目录和备份目录，再使用计划输出的 SHA-256 执行：

```sh
python3 /srv/jindu/releases/0.15.0/deploy/portable/manage.py apply \
  --plan /srv/jindu/updates/plan-0.15.0.json --sha256 <计划的完整SHA-256>
```

工具锁定容器和镜像身份，等待后台完成当前任务，再停止网页。超过等待时间会退出，不强制终止进程。停写后，将数据、私密配置及其他绑定挂载制作成完整备份，并在同一台服务器的新目录解包，逐文件核对校验值和数据库完整性。备份和校验副本不会自动下载，也不会自动清理。

新网页先启动并检查数据库版本；维护期间 API 返回 503，后台暂停领任务。网页和后台健康检查通过、业务记录核对一致后才结束维护。更新过程中不运行初始化，不更换账号或密钥。旧容器停止后保留，避免两个后台同时写同一数据库。

成功后，`updates/active.json` 记录当前 Compose 文件的位置。**下一次更新必须使用该文件所指向的 Compose**，避免误启旧版本。每次更新都会留下 `receipt.json`、完整备份及恢复校验目录。需要的可用空间至少为备份源大小的两倍加 100 MB，另须预留镜像构建空间。

启动失败时，只有数据版本与旧程序兼容，工具才恢复旧程序；它不会用旧数据库覆盖新记录。命令被中断时，先查看回执，再执行 `manage.py recover --receipt <本次回执完整路径>`。已完成的更新不能复用该恢复命令；后续回退必须作为新的变更评估。备份的字节和 SQLite 校验不等同于业务恢复验收；需要恢复完整数据时，先在服务器独立目录按清单的原路径、权限和 UID/GID 恢复，验证登录、附件、任务和订阅，再决定替换正式目录。

v0.15.0 首次将现有数据库登记为 schema 1，并增加附件检索索引，业务字段不变。此版本接受 schema 0/1，允许失败后恢复 v0.14.17；后续版本须分别声明兼容范围。程序拒绝打开比自身更新的数据库，迁移失败会回滚该次迁移事务。工具目前支持本机绑定目录、一个网页和一个后台；外部网络、命名数据卷及额外服务依赖需要单独制定方案。

同域名和订阅密钥不变时，可继续使用原日历订阅地址；更换域名后需要更新订阅链接。数据目录应放在本机磁盘，不使用网络共享盘运行 SQLite。
